# Umpire v1 discrepancy ledger

This ledger freezes the Umpire document v1 contract before the JSON Schema composition profile is implemented. It compares the normative decisions in the interop plan with the public meta-schema, `@umpire/json`, and `umpire-go-gen` as inspected on 2026-08-06.

The contract is normative. Rows V1-01 to V1-12 record implementation drift or a fixture gap and introduce no new v1 behavior. Rows added after the freeze say what they add and the spec release that adds it. Stage 2 owns implementation alignment. Stage 1 adds the shared cases that make each row observable.

## Membership against array-valued fields

Added on 2026-11-15 for umpire-spec#8. V1-13 was not part of the Stage 1 freeze. Before it, no fixture ran membership against an array-valued field, and the runtimes disagreed.

| ID | Normative decision | Public meta-schema | `@umpire/json` | `umpire-go-gen` | Shared fixture and action |
| --- | --- | --- | --- | --- | --- |
| V1-13 | Added in v1.2.0. `contains` (`field`, primitive `value`) is true when the field's array value holds an element equal to `value`. A value that is not an array gives `false`. Every membership op (`in`, `notIn`, `fieldInCond`, `contains`) uses JSON equality with no coercion: `true` is not `1`, and `"22"` is not `22`. `in`, `notIn`, or `fieldInCond` targeting a field declared `"isEmpty": "array"` is a definition error. So is `contains` targeting a field declared `"isEmpty"` as `string`, `number`, `boolean`, or `object`. Both errors are raised at schema validation for every expression position at any depth. On any other field, `in` against an array value is `false` and `notIn` is `true`. | Aligned: closed `contains` variant with a primitive `value`. The `isEmpty` cross-check is semantic. | Drift: no `contains` op; `in`/`notIn` on an array field compile to a constant. The compiler receives field names only, not definitions, so the `isEmpty` cross-check needs the definitions passed in or a separate walk. | Drift: array-typed `in`/`notIn` emit Go that does not compile (umpire-go-gen#14). No `contains` op. `isEmpty: "array"` is typed `[]string`, and the `contains` helper takes `[]string, string`, so array fields need an element representation that holds any JSON primitive (`[99, 22, 7]`, `["22", 23]`, `[true, null]`). The conformance harness discards decode errors. | `array-membership` fixture. `v1-baseline-failures`: `in-targets-array-field`, `nested-not-in-targets-array-field`, `in-under-disables-when`, `not-in-inside-any-of`, `in-inside-either-of-branch`, `field-in-cond-targets-array-field`, `contains-targets-string-field`, `contains-targets-number-field`, `contains-targets-boolean-field`, `contains-targets-object-field`, `contains-unknown-field`, `contains-missing-value`, `contains-non-primitive-value`. Every interpreter and the generator add `contains` and both definition errors. Other drift: `umpire-py` evaluates `in` with Python `in`, where `True == 1`, so it breaks the no-coercion rule. `umpire-dart` evaluates `contains` but does not require a primitive `value`, has no `isEmpty` cross-check, skips `dependencies` in sub-rules when walking expressions, and its conformance harness asserts a throw without checking `errorIncludes`. |

## Fixture conventions

`conformance/fixtures/v1-baseline.json` is an accepted public document and contains the normative status cases named in V1-06, V1-08, V1-09, and V1-10.

`conformance/failures/v1-baseline-failures.json` contains both kinds of rejection:

- The default is an implementation-level rejection whose `schema` remains valid against the public meta-schema.
- `metaSchema: "reject"` marks a document that the public meta-schema must reject as well. `validate.mjs` checks these cases with the same AJV contract used for the public schema.

The fixture IDs are intentionally stable. Runtime implementations must consume the fixture index rather than copying the examples into implementation-specific tests.

## Stage 1 disposition

Every row has an owner and a shared fixture or existing fixture reference. No row is an unresolved normative decision. Stage 1 does not change either sibling implementation, the JSON Schema composition profile, or the Umpire v1 semantics; it records the discrepancies and freezes the acceptance/rejection evidence for Stage 2.
